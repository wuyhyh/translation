<!-- page: 543 -->

_end_static 只不过是 _ebss 内存位置的别名，即 .bss 段的末尾。_Heap_Size 由我们固定，它确立了堆（400 字节）的大小。最后，_Heap_Limit 包含的只不过是堆内存的最终地址。

¹⁶ 在这里，我们可以使用另一种方式来指示堆溢出。例如，可以调用一个全局 error() 函数，并在其中采取适当的措施。然而，这通常是一种编程风格，因此请根据需要自由安排该代码。

关于链接器脚本符号的说明

![Image from PDF page 544](../images/page-0544-image-01.png)

在本章中，我们大量使用了从 C 源代码中定义的链接器脚本中的符号。对于每个符号，我们都定义了一个对应的 extern uint32_t _symbol 变量。每次我们需要访问该符号的内容时，我们都使用 &_symbol 语法。这可能会引起混淆。

链接器脚本中符号的处理方式与 C 语言不同。在 C 语言中，符号是由符号、其内存位置和值组成的三元组。链接器脚本中的符号是元组，由符号及其内存位置组成。因此，符号是内存位置的容器，就像指针一样，没有值。所以以下指令：

```text
extern uint32_t _symbol;
uint32_t symbol_value = _symbol;
```

是完全无意义的（_symbol 没有对应的值）。

虽然当 _symbol 是一个内存位置时，这种处理链接器符号的方式显然是合理的，但如果它是一个常量值，则会导致大量错误。例如，要在 C 语言中获取 _Heap_Size 的值，我们必须使用以下代码：

```text
unsigned int heapSize = (unsigned int)&_Heap_Size;
```

_Heap_Size 再次将堆大小作为地址（即 0x00000190）包含在内，但它不是一个有效的 STM32 地址。通过使用 objdump 工具并带有 -t 命令行参数检查最终二进制文件的符号表，也可以分析这一事实。

### 20.2.5 在编译时检查堆和栈的大小

微控制器具有有限的内存资源。特别是对于 Value-lines STM32 微控制器，很容易超过最大 SRAM 内存。我们也可以使用链接器脚本添加一种关于最大内存使用的“静态”检查。以下链接器脚本部分有助于确保我们没有使用过多的 SRAM：

```text
_Min_Stack_Size = 0x200;
/* User_heap_stack section, used to check that there is enough RAM left */
._user_heap_stack :
{
. = ALIGN(4);
. = . + _Heap_Size;
. = . + _Min_Stack_Size;
. = ALIGN(4);
} >SRAM
```

使用上述代码，我们在最终的二进制文件中定义了一个“虚拟”段。使用位置计数器运算符（“.”），我们增加该段的大小，使其尺寸等于

<!-- page: 545 -->

最大堆大小和“估计”的最小栈大小。如果 .data、.bss、栈和堆区域的总和大于 SRAM 大小，链接器将发出错误，如下所示：

```text
arm-none-eabi-g++ ...
./src/ch10/main-ex5.o
../../../../arm-none-eabi/bin/ld: nucleo-f401RE.elf section `._user_heap_stack' will not fit i\
n region `SRAM'
../../../../arm-none-eabi/bin/ld: region `SRAM' overflowed by 9520 bytes
collect2: error: ld returned 1 exit status
make: *** [nucleo-f401RE.elf] Error 1
```

重要的是要强调，这是一种静态检查，与固件在运行时的活动无关。检测栈溢出需要不同的策略，并且很难为嵌入式系统找到完整的解决方案。我们将在第 22 章中分析这个主题。
